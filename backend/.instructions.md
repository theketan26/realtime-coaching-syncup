# Backend Database Instructions

## Database Query Management

### Primary Reference File
- **query.sql** is the primary source of truth for all database schema and migration changes
- Always consult `@file:query.sql` before proposing or making database changes
- When asked about database schema, check query.sql first to understand current state

### Adding Database Changes
When making changes to the database:

1. **Append to query.sql** - Add new queries at the end of the file, after existing changes
2. **Never modify existing queries** - Preserve all previous migrations for historical reference
3. **Required Structure for Each Query:**
   ```sql
   -- [DESCRIPTION OF CHANGE]
   -- Purpose: [What this change accomplishes]
   
   -- Query that makes the change
   [YOUR SQL QUERY];
   
   -- Check if successful
   -- Failure check: [Description of what should exist if successful]
   SELECT ...FROM ... WHERE ...;
   
   -- Revert query (if needed to rollback)
   -- Revert: [Reason this might need to be reverted]
   -- [REVERT SQL];
   ```

4. **Comment Every Query** - Include:
   - Description of what the query does
   - Purpose/motivation for the change
   - Clear labels for failure checks and revert queries

### Example Format
```sql
-- Create users table with authentication fields
-- Purpose: Store user account information and credentials

CREATE TABLE IF NOT EXISTS users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Check if users table was created successfully
-- Failure check: Verify table exists and has required columns
SELECT table_name FROM information_schema.tables 
WHERE table_schema = 'public' AND table_name = 'users';

-- Revert: Drop users table if migration needs to be rolled back
-- DROP TABLE IF EXISTS users;
```

### Query Validation Rules
- Each query must include a failure check SELECT statement
- Failure checks verify the change actually occurred (table created, column added, etc.)
- Include commented revert queries for all DDL (CREATE, ALTER, DROP) statements
- For DML changes (INSERT, UPDATE, DELETE), include the previous state restoration in comments

### Workflow
1. When I need to make a database change, I will:
   - Check current query.sql to understand existing schema
   - Propose the new query with all required components
   - Create the query with proper comments and revert information
   - Append it to query.sql

2. Code changes that depend on database schema:
   - Verify schema changes are in query.sql first
   - Update application code to match the schema defined in query.sql
   - Always reference query.sql as the schema source of truth

### Key Principles
- **Single Source of Truth**: query.sql is never the source of confusion
- **Reversibility**: Every change can be undone via the included revert queries
- **Transparency**: Comments make the intention and impact of each query clear
- **Auditability**: Full history of changes preserved in query.sql

# SQL table convention for backend/query.sql

When writing `CREATE TABLE` statements in `backend/query.sql`, every table must include the following columns:

- `id` — a numeric primary key with sequential auto-increment behavior
- `createdAt` — a datetime/timestamp column with a default value of `NOW()` (or `CURRENT_TIMESTAMP`)

This rule applies to all table definitions in `backend/query.sql`.

Example:
```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  createdAt TIMESTAMP NOT NULL DEFAULT NOW(),
  name TEXT NOT NULL
);
```

## Type definition synchronization

Every table created or modified in `backend/query.sql` must have a corresponding TypeScript type definition maintained in a `types/` directory.

- Type definitions should reflect the exact structure and column names of tables in the database
- Whenever a table is added, modified, or removed in `query.sql`, the corresponding type file must be updated
- Type files should be created/maintained to match each table's schema
